# C3a: Today, Board and item detail/editor

These shared screens are wired into the existing shell on Android and desktop through `LocalScreenServices` (set inside the trust/PIN gate). `AppServices.data` supplies generated read models and repositories. `settings.memberId`, never member-list ordering, identifies the caller; Today uses the member's zone and injected `AppClock`, rolls over at member midnight, and memoizes sections. Needs an owner ignores Mine and includes only the current Today/This-week window [today, today + thisWeekDays); expired/done/skipped rows are excluded. Times use platform locale-aware formatting in the member zone (floating wall times remain local); recurrence has a readable summary. Member chips use server #RRGGBB and initials. No optimistic authoritative mutation, offline queue or local snooze is introduced.

## Navigation and extension points

- `AppRoute.Today`: persisted server section order/scope/window, member initials, completion/Take, pinned-list placeholder (C5), pending/read failure/empty states.
- `AppRoute.Board(filter)`: household/mine/member filters over the server projection. Four fixed columns; server owns next-open-series and seven-day Done retention. Long-press drag, Alt+arrows, move buttons and custom accessibility actions share `BoardDrop` semantics. The index excludes the mover and counts only visible cards.
- `AppRoute.Item(id, occurrenceId = null)`: backward-compatible optional occurrence context for recurring edits. Cached projections can seed detail before the item repository has it. Item actions use server capabilities; no cached role inference. Delete asks confirmation. Address has a copy action.
- `AppRoute.NewItem`: new additive route for creation, available without any saved item ID. C3b route availability should permit it locally, like Today. Detail uses an in-screen editor, not a new saved editor route.
- `TodayContent`, `BoardContent`, `ItemDetailContent`, `EditorForm` are typed presentational composables with callbacks; controller/device tests do not require live trust. C4 can add a real snooze callback once its local implementation exists; C5 can fill pinned-list/detail collaboration content. Calendar, settings, resume availability and M4 gate tooling are C3b-owned.

## Write safety and forms

`ScreenSession` is application-scoped, memory-only in production AppServices. Writes run in the session application scope, survive route removal, and cancel at identity change. Requests/drafts survive PIN relock/Activity recreation, but are cleared on household identity epoch changes. `HouseholdData.bindTrust` adds an optional `onIdentityEpoch` callback, delivered on Main; existing callers remain source compatible. Tests without production services can omit the session.

A successful item save retires its session draft and baseline inside the write itself (also on an identical retry), so a save that completes after the user left the editor is not resent by the next Edit; only the baseline generation that save diffed against is retired. While editing, every 422 field error is visible: errors for a rendered text control appear under it, and every other key (`occurrence_id`, `override`, `assignees`, a timing field of another kind, ...) is listed at the top of the form (`editorTextControls` is the single source for both). Today re-reads the wall clock whenever its screen starts or resumes (Activity start after sleep, desktop window refocus) and on every system wake signal (`AppServices.systemResumes`; desktop publishes logind `PrepareForSleep(false)` from DesktopLive's existing resume monitor, which arrives without any lifecycle change). While visible, its timer also re-checks the wall clock at least every 60 s (`TODAY_WALL_CLOCK_RECHECK`) and updates only when the member-local date changed; it stops while Today is not visible. Monotonic delays stop while a device sleeps, so a midnight timer alone could show yesterday's sections after a desktop wake.

`ScreenWrites` retains an immutable request closure/key for an unconfirmed reply (including a 5xx, a non-problem error page or an undecodable reply) or cancelled request. Explicit retry sends the same body/version/key; it never automatically replays an ambiguous outcome or a version conflict. Success with `refreshPending` means refresh the read, not resubmit. A sealed validation failure permits a corrected new request. A version conflict displays field-level yours/current differences for only the user-changed keys; reapply is explicit, uses `current.version` and a new key, and requires current edit capability. Discard closes the editor and refetches. Conflict warnings never block save. A create with warnings/pending refresh remains on the success summary until the user opens the created item, rather than hiding its warnings by navigating immediately.

Board adds backward-compatible parameters to `occurrences.move`: `visible` filters the current projection before selecting bounds; `replay: BoardMoveReplay` retains bodies by operation key and exposes `activeKey`. A 422 stale neighbour refetches and constructs a new body's bounds with a new key. A subsequent relock/cancellation retries that actual key/body, even after the cached projection changes. Callers retaining an ambiguous move must retain the replay object and pass its active key to `ScreenWrites.submit(activeKey = ...)`.

The editor uses typed generated create requests and presence-aware `ItemEdit` patches diffed against an immutable form baseline (explicit null clears, omissions untouched). Reapply retains only those changed fields against the current version: never the entire stale draft. Drafts track user edits with an explicit per-field presence set, including changes to default values and values restored to their seed; this never compares default-dropping JSON encodings. Changing scope resets timing fields (kind, time mode/zone, all-day, anchors, RRULE schedule controls and completion intervals) to the chosen scope's seed while preserving metadata edits, including stopping recurrence. The first explicit scope choice also resets timing: a restored draft may have a tail baseline even though the UI starts at All. Only reselecting an already-chosen scope preserves all edits. The form explains the reset and asks users to choose scope before adjusting timing. Calendar tails seed anchors from the selected occurrence and reduce COUNT by its zero-based seq, so pre-scope head timing cannot leak into tail patches. Title-only tail patches omit all timing/RRULE fields; completion series never offer this-and-future. Unchanged occurrence saves send no overrides and cannot detach. Fixed instants include offsets; floating locals are normalized with seconds. The time-zone field validates IANA names, with common-zone picker shortcuts. It includes kind, anchors, all-day, RRULE subset controls, exact completion interval, missed policy, buffers, estimate, priority, address, subject and visibility. Recurring metadata edits require an explicit scope choice. This occurrence sends only `override_*` anchor fields; fixed instants are converted into the item's zone, following server fold-earlier/gap-next-valid policy. Per-occurrence edits cannot change series metadata. Assignees, viewers and reminder offsets use their own versioned endpoints (explicitly whole-series controls); those fields are not legal item PATCH fields. Server validation fields are displayed, including override-to-visible-anchor mapping.
