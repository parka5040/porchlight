# C5 collaboration clients

## Binding interfaces for C4/C6

`AppServices.data` additionally exposes `lists`, `comments`, `attachments`. All flows contain generated OpenAPI models, not screen DTOs. Existing services/constructors remain compatible. Production passes `FileAttachmentStore`; shell tests default to memory storage. SQLDelight disposable schema version 3 scopes list/entry rows by (id, occurrence), with the empty scope for templates/persistent lists, and retains CacheList, CacheEntry, CacheComment and CacheAttachment (metadata JSON only). Android/desktop existing mismatch handling recreates the read cache.

- `lists.lists`, `observe(id, occurrenceId)`, `refresh(itemId?)`, `get(id, occurrenceId?)`, `refetchByIds(listIds)`, create/edit/delete/viewers/add/editEntry/archive/check/clear/move. Persistent lists split checked entries into Got it; per-occurrence lists keep checked entries in entries and uncheck uses each entry’s checked_at; `propertyEntries` is the generated Kotlin name for wire `entries`. Entry patches use presence-aware JsonObject so null clears qty/url or appends a move. Rename uses `edit`; visibility/viewers use `change_visibility`; Clear Got it uses `manage`, while entry management uses `manage`, checks use `check`, deletion uses `delete`. No role grants override visibility.
- `comments.comments`, `forItem(id)`, `page(itemId, cursor?)` (50 rows), first-page `refresh(itemId)`, `refetchByItemIds(itemIds)`, create/edit/delete. Opening a thread reads the live cache tail, not `refresh`. Item-scoped `refetchByItemIds` walks 50-row pages only through the captured cached UUID horizon (at least the first page), reconciles edits and missing/deleted IDs in traversed ranges, and evicts their attachments; it never walks uncached history. Rows changed in the cache since the request are not evicted by a missing-row result. `canEditComment` uses the original created_at plus inclusive 15 minutes, author ID and deletion state. Highlighting uses returned mention IDs only. UI member selection inserts plain @displayName; the server parses it.
- `attachments.attachments`, `forItem(id)`, upload/delete/download/open. `refetchByItemIds` resnapshots: there is no attachment-metadata GET or collection route. `download(row, thumbnail)` uses attachment-ID GET through the same pinned mTLS client; never hashes or filesystem paths. Upload accepts a bounded ByteArray, a progress callback and an optional retained key. UI cancellation is ambiguous and its ScreenWrites closure retains identical bytes/name/MIME/key for explicit retry. No offline writes/queue or automatic replay of IO failures.
- C4 tickles: list/entry events supply `list_id`; call lists.refetchByIds. Comment/attachment events are item-scoped; use comments.refetchByItemIds / attachments.refetchByItemIds. `cache.evictList(id)` evicts entries too. Existing `sync.evictItem` now also evicts attached lists, entries, comments and attachment metadata. Application-lifetime metadata observation removes private attachment/view files after eviction; failures leave bytes inaccessible through repositories until 180-day cleanup. Identity clear awaits all private file deletion.
- `ListMoveReplay` must survive ambiguity, like `BoardMoveReplay`. Pass `activeKey = { replay.activeKey }` to ScreenWrites.submit; retry the actual active key/body/version. A 422 invalid-reference/stale-neighbour refetches the same selected occurrence and constructs fresh visible neighbours with a NEW key. Transient 409 + Retry-After retains the same key. 409 version-conflict is presented for explicit compare/refetch, never silently reapplied.

Snapshots stage/promote all new tables in the existing single transaction. Newer list/comment/attachment/entry receipts protect rows the older snapshot actually contains; missing rows never resurrect. Deletion receipts remove older snapshot copies. Per-occurrence snapshots are templates: scopes whose occurrence remains in the snapshot survive atomically (merged template structure/ACLs, independent checks); scopes outside that window are dropped, including newer scoped receipts. Cleanup also drops scopes whose occurrence has left the cache's 180-day window. At most 32 occurrence-scoped lists are retained household-wide, oldest fetched first for eviction; templates/persistent lists do not count. Dropping a scope removes its entries and receipts, never another scope's checks. get(id, occurrenceId) refetches authoritative checks; a scoped 404 or the server's 422 validation-failed with an occurrence_id/invalid-reference field error evicts only that scope. Unrelated 422s/transient errors remain cached and are surfaced. refetchByIds tries the captured retained scopes and all requested IDs, ignoring eviction failures and reporting the first other failure only after the batch; cancellation still stops immediately. Thus normal tickles cost at most requested IDs + 32 GETs, independent of browsing history, and never guess/reuse checks across occurrences. Missing list/item snapshots (or an unscoped 404) evict all scopes. Successful comment/list/add drafts clear; failed writes retain drafts, and entry editing remains open until success. Entry responses publish exact returned entry data without guessing the list's new version; the versioned parent is refetched. Writes queue a full sync behind in-flight sync and mark refreshPending if follow-ups fail, without replaying the mutation. New creations omitted by an older snapshot are repaired by that queued authoritative resnapshot.

`AppRoute.Lists(listId?, occurrenceId?)` is additive/backward-compatible; local resume uses cached visibility/capabilities, and entry loads refetch the requested occurrence. Attached-list discovery uses the server's item-filtered collection (including split ancestors); the UI does not infer ACL or series ancestry. Today uses the pinned list setting, refetches templates, and offers standalone/persistent checks. Item detail adds CollaborationSection after existing item controls.

## Platform storage and picking

Android uses scoped photo picker (open-document fallback below API33), open-document files, and camera intent with app-owned FileProvider output. Only attachments/ under private cache is shared by explicit read grants; no external storage permission, broad provider root or persistent URI grant. Camera permission refusal/cancellation is recoverable. Desktop uses a Swing file chooser. Both reject >25 MiB before sending, decode server thumbnails, and open private downloaded files only after an explicit user action. Desktop bytes live in `$XDG_CACHE_HOME/porchlight/attachments` (fallback `~/.cache/porchlight/attachments`). No automatic save outside app storage is implemented. Cached files use validated local ID/version/epoch keys, atomic replacement, owner-only permissions and 180-day cleanup. Viewer filenames are ID-based and use the server MIME extension, never original_name. Uploads mirror the server's 30-second idle / ten-minute total deadline.

Desktop viewer files (`writePrivateDesktopFile`) are owner-only from creation: the cache directory is created 0700 (an existing one is narrowed to 0700), the bytes go to a `-part` staging file created 0600, which is renamed over `<id>-view.<ext>`; a symlink there is replaced, never followed. A symlinked, non-folder, foreign-owned, unwritable or non-POSIX cache directory fails closed with `PrivateDirectoryUnavailable` (the attachment does not open); there is no not-private warning path because this is Porchlight's own data directory. The viewer then says which folder is unusable and why, that it must be a folder the user owns with owner-only access, and that retrying alone will not help (`attachmentOpenError`); download, visibility and lock failures keep the generic "Refetch or unlock before retrying" message.

Picker and camera results never go to a composition-bound callback. Every full-screen picker or camera STOPs MainActivity, which relocks the PIN gate and discards the trusted subtree; rotation recreates it. Each pick is a request in the identity-scoped `ScreenSession.attachmentPicks` that records its item and target comment at launch; the Android helper Activity delivers through `AttachmentPickRegistry`, the desktop chooser runs in the application scope. The result (bytes in memory only) waits until that item's collaboration section is composed again, i.e. after unlock, then uploads once to the launch target. Identity change clears it; process death drops it (the captured photo is deleted either way). The helper Activity handles configuration changes itself so a rotation cannot cancel reading a returned pick.

Packaged desktop viewer and emulator external-activity results remain unverified here.

## Bounded thread presentation

Opening a thread shows the newest 50 cached comments ordered by created_at then ID, including offline; no comment HTTP request or history walk is needed. The window is derived on every cache update, so sync/SSE and the user's committed post appear immediately even on a full window. Show older expands the rolling tail budget by one 50-row page; cached history works offline without HTTP. Only when that cached budget is exhausted does an explicit Show older fetch one oldest-first server page, never automatically walk to the tail. Show latest resets the budget to 50. Selection retains only the requested presentation budget while scanning the cache, not a sorted copy of the full history. Older pages cost memory/composition only when explicitly requested, not on opening or live tickles.

Partial `page` results merge metadata without deleting off-page comments/attachments. Complete first pages, cached-horizon `refetchByItemIds` and normal snapshot/event eviction reconcile deletions. Manual Refresh collaboration uses that cached-horizon contract plus snapshot refresh, not a first-page-only refetch. Paging errors are separate from attachment/picker errors; successful history loads never clear an unrelated error. Snapshots remain the spec's complete read cache (metadata only), not a paginated mutation queue.

Attachment rows are capped at 20 per batch, scoped to the displayed comment window plus item-level attachments, with Previous/Next controls. Thumbnails load only on Show thumbnail; at most one preview's bytes/decoded image is retained in composition. Hiding/changing page/preview releases that state and cancels its load. Android/desktop decode on Dispatchers.Default rather than during composition. Full opens are serialized in the screen, and the repository gates full network downloads to one (thumbnails remain two). Private disk cache and the transport's 25 MiB transfer bound are unchanged.

409 idempotency-in-progress and exhausted unsealed contention keep the original operation/key for identical retries across create/add/comment/upload; they are not shown as a definitive rejection. Explicit abandonment still warns that the operation may have committed.

## Authoritative read denials and retained search results

Item GETs and comment collection pages (`comments.page`, so also `refresh` and `refetchByItemIds`) treat 404 or 403
forbidden as parent visibility loss. The repository eviction boundary
removes the parent and all collaboration metadata and awaits original, thumbnail and private viewer-file removal,
even if the caller is cancelled and without the optional lifecycle watcher. Attachment/thumbnail path denial evicts
ONLY that attachment and its files, then confirms the parent with item GET: only that GET's 404/403 forbidden evicts
the parent (a deleted attachment/comment or missing blob does not prove parent visibility loss). It attempts all file
removals; failures are suppressed on the original API problem, not substituted for it. Step-up-required/401/transient/
offline failures retain cached parent content. A session change during that eviction propagates as cancellation:
no parent GET or eviction runs for the old session. A cached download rechecks live metadata after reading bytes.
Platform viewer-file creation must use `attachments.open(row) { bytes -> actions.open(...) }`, which fences the
metadata check and platform write/open against eviction and identity change; do not download then open unfenced.

Lists search keeps results outside the authoritative read cache. Confirmed list/parent removal prunes retained
hits (including snapshot removal), and opening a result always GETs its ID/scope before selecting it—even if
that ID is already selected. It never installs an old search ListResponse into the cache. Search failures cannot
restore entries, capabilities or visibility. Eviction markers are in-memory screen-cache state, reset on identity
clear; a freshly authorized read can restore visibility. Unscoped list GET forbidden also evicts the list.
