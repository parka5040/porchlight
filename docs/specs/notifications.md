# Notifications (S6a)

## Public contract

- `GET /v1/notifications?unread=true&cursor=&limit=`: recipient-private released inbox, descending UUID keyset, default 50/max 200. Cursor is authenticated and bound to household/caller/recipient/unread. App super admins do not inspect another recipient's inbox. Agents' ordinary inbox is also self-only.
- `POST /v1/notifications/{id}/read` and `/v1/notifications/read-all`, body `{}`: monotonic, idempotent actions (no If-Match); no-op reads write nothing. Hidden/other-recipient path rows are 404. Read-all touches only visible released rows.
- `GET/PUT /v1/me/notification-prefs`: canonical self resource `{member_id,prefs,version}`. PUT replaces all prefs, requires If-Match; stale 409 includes current. No-op replacement writes nothing. Category defaults on; quiet times unset; default reminder offsets empty until configured. Offsets are unique integers 0–525600 minutes, maximum 16 per kind. Quiet start/end must both be null or distinct valid whole-second local times (fractional seconds rejected). Times normalize to HH:MM:SS.
- `GET /v1/admin/notifications?member=`: agent-only surface, admin PAT required; inspection uses the target recipient's authoritative visibility, not an agent visibility bypass.
- Snapshot includes `notifications` and `notification_prefs`, assembled inside its existing REPEATABLE READ transaction and matching outbox cursor. Inbox and source data never authorize reads through a derived projection.
- `porch notifications list [--unread] [--cursor] [--limit]`, `inspect --member`, `read ID`, `read-all`, `prefs`, `set-prefs --file FILE --version N`; all support global `--json`.

## Routing and persistence

`notification_events` and `pl_emit_notification_event` remain S4b's shared producer contract. S7b comment/mention and S8b load-conflict/suggestion events are consumed without duplicating their producers. This stream owns only processed_at and notifications.

| Source | Recipient | Suppression/dedupe |
| --- | --- | --- |
| task_events.assigned | assignee | self notification suppressed; live login profiles only; task-event UUID dedupe |
| status_changed/completed/reopened | owner (reopened maps to status_changed) | self suppressed; task-event UUID dedupe |
| new hard conflict | member whose calendar conflicts | canonical occurrence pair + member; excludes pending counterpart projections; same-item recurrence overlaps remain eligible |
| due scheduled_reminders | member | current projections/live readable item/open occurrence; occurrence/member/reminder tuple; local_alarm=true |
| unassigned dependent appointment | all live users/super admins | weekly Sunday 18:00 in household zone before coming Monday–Sunday week, elapsed 48h and 24h before effective start; occurrence/member/slot/due-instant for every slot; rescheduling re-arms countdowns |
| attempts transitions below 5 → 5 | live super admins | item/requested_gen/member; generic operational alert, no title/item-scoped ACL reference |
| agent business write | same recipients | agent:<name> captured by existing event producer and displayed in summary |
| backup_stale (0057 registry INSERT, R53) | live super admins | system producer hourly; last success (or household creation) strictly older than 26h; recipient + latest success UUID (initial if none) dedupe per stale episode; fixed operational template, activity delivery |

Default reminder offsets are member-specific fallback only when an item has NO explicit item_reminders. Synthetic reminder UUIDs are stable per reminder-origin/member/offset. Migration 0068 adds immutable `items.reminder_origin_id` and `item_reminders.delivery_id` (NULL means the row's own ID, preserving all pre-upgrade witnesses). A split copies the default origin and explicit delivery identities to the tail before transferring projections, without remapping dedupe keys. Head-snapshot production concurrent with a split and future regeneration after a backward clock correction therefore use the same occurrence/member/reminder witness. These are copied values, not FKs to the head: later edits or purge cannot change the tail's identity. `scheduled_reminders.reminder_id` is a logical delivery identity rather than an authoritative item_reminders FK. Projection rows keep their `id` across regeneration (including splits) while the member/occurrence/reminder tuple and `fire_at` are unchanged. Projection regeneration carries forward already-due rows only when they have no emitted reminder dedupe event and their member/occurrence/reminder/fire-at tuple is still present in the authoritative regenerated schedule. The projection DELETE and due/unemitted filter share one statement; fired obligations are retired during regeneration while their dedupe witness exists, and the carry-forward additionally drops any tuple whose fire_at is older than the 90-day event-retention horizon (R74, below). Unrelated buffer/duration edits and recovery cannot erase that pending delivery obligation; rescheduling, removing offsets/recipients, closing or deleting the item still invalidate obsolete reminders. Newly introduced overdue offsets do not generate retroactive reminders. Replacement and carry-forward are atomic; scheduler excludes pending projections and the event dedupe tuple prevents repeat emission while its witness is retained (see lifetime limitation below). No agent writes to generated inbox/source/reminder data.

The consumer takes member FOR KEY SHARE SKIP LOCKED before serializing each recipient on notification_prefs, then discovers at most 500 events sorted by created_at/id in one actor-attributed transaction. Before touching notifications it reserves all referenced items in UUID order with FOR KEY SHARE SKIP LOCKED (a busy/missing item defers the whole recipient), then locks all surviving batch events FOR UPDATE in UUID order. After event locks, it reserves every possible existing coalescing target in UUID order: matching digest quiet-end identities (including released/read rows), plus unread non-digest windows overlapping the batch time span. This follows purge's item → event(id) → notification(id) order and retention's event(id) → notification(id) order; processing remains chronological. Read-all and held release/suppression also lock their notification candidates in UUID order. Locks survive successful event savepoints; no later event lock is acquired after a notification lock. Each event has a SAVEPOINT: link + row + processed_at + outbox are atomic. Deadlock (40P01), serialization (40001), lock timeout (55P03), and statement cancellation/timeout (57014) roll back only the failed event: earlier successes commit and later events in the locked batch still run. Transient failures use durable recipient backoff (2/4/8/16/32/60 seconds, capped at 60) and per-event retry_at. For six hours from the immutable event created_at (injected clock), they record safe failure metadata but no new poison strikes; prior data strikes remain. At age >= six hours, every further transient failure spends an ordinary strike; five strikes poison/skip the event. Six hours tolerates ordinary contention/outages without turning a repeatedly data-dependent timeout into infinite retry; event age deliberately bounds even delayed/restarted consumption, without relying on process-local attempt history. Cost: an outage longer than the grace can drop a delivery, but its source event and existing inbox state remain. A backed-off transient event does not hold the digest release hostage: release waits for other due backlog, not that isolated event. A later successful retry still coalesces under the same digest/window identity and clears retry metadata; release never resets active event backoff. At most 50 eligible recipients are attempted per pass. Each recipient has an isolated transaction; failures cannot block later healthy recipients or the separate release pass. Internal notification_event_delivery records per-event strikes (attempts, zero allowed during transient grace), retry_at, last_error (safe class only, including statement_cancel for 57014) and poisoned_at (0065). Non-transient failed events retry after 2/4/8/16 seconds, including across restarts; on the fifth failure they are marked poisoned/skipped and processed_at is set, so later events and held digests flow. Successful event delivery clears its retry metadata. Timeout-class transients (55P03 lock_timeout about 5 s, 57014 statement_timeout about 30 s) are correlated and slow, so a recipient pass tolerates at most ONE (including a timeout that is the fifth, poisoning strike: the event is poisoned and the pass still stops): on the first, earlier successes are kept, the pass commits and stops for that recipient, and the failed event's own retry_at (2-60 s, growing with the recipient attempt count) excludes it from later passes so the later events run on the next pass without parking the recipient (its recipient retry_at is set to the pass time, attempts still grow). A pass therefore holds the recipient's prefs/event/notification locks for at most one timeout, and other recipients are not stalled. Fast transients (40P01/40001) keep per-event isolation and continue the batch, since each fails immediately and costs no wait. Candidate discovery excludes backed-off recipients before LIMIT; the consumer rechecks backoff under prefs serialization. Poisoned metadata remains SELECT-readable by agent administrators for inspection; no new HTTP admin surface is introduced. Skipping emits a warning with member/event UUIDs, attempt count and safe error class, never raw errors or payloads. Recipient-wide infrastructure/prefs/release failures retain notification_delivery_retry exponential delay (2–60 seconds, exponent capped at 6); successful consumption or actual release clears it. Prefs reads explicitly project the public columns, so adding internal settings columns cannot poison decoding. SKIP LOCKED and atomic event rollback make concurrent workers/restarts safe. Events for dependent/deleted profiles are processed without delivery. Disabled categories and inaccessible items are consumed without delivery.

30-second windows are anchored and half-open (`start <= event < start+30s`), not sliding. Local-alarm history is kept separate from event-alert summaries. Business categories share a recipient window; mixed categories use activity. Read notifications never reopen during coalescing. Quiet hours use each event's timestamp in the member's authoritative zone (dependent effective zone = household), including delayed/restarted processing. Reminders bypass quiet hours. Non-reminders form one digest row per recipient/quiet-end instant; release waits until currently due event backlog is consumed (except isolated transient events currently backed off), preventing a healthy 500-row boundary from splitting the morning batch. Digest identity lookup is serialized by prefs and includes already-released/read rows: a producer committing after quiet-end appends to the same row, emits an update rather than a second created tickle, and never clears read_at. The backlog check is a release optimization, not the identity boundary. Release rechecks the current Digest toggle under the prefs lock; disabled Digest deletes undelivered digest rows/source links without emitting alerts or releasing inbox entries, while retaining immutable source events and already-released history. Fold → earlier endpoint, gap → next valid time, same as core time. Membership compares the resolved start/end instants (half-open), including the preceding-date overnight interval, so repeated wall times cannot temporarily disable quiet hours. The notifier clock is injected through item_clock; scheduler callbacks receive their injected clock and freeze the event timestamp transaction-locally. The clock GUC is honored only for app/system or superuser/system writes; raw-SQL agents cannot forge it.

`notification_sources` retains immutable event links. Every fetch recomputes visible count, summary and references from individually authorized source items. No summary ever contains an item title or producer-controlled payload. Lost visibility hides a single-source notification; a mixed batch keeps only readable sources/counts. Stored generated count/summary is not an authorization source. Source links cascade on event/notification purge. Row-level item refs become NULL on physical item purge (0021), preserving unrelated coalesced sources. O2 owns 90-day retention; full DB export/backup automatically includes both tables/prefs.

Digest merges increment the stored count and rebuild its count-only template from that value, consuming only the new event rather than reloading historical sources. This survives worker restarts and late appends to read/released digests. Stored counts describe consumed events, not current visibility (or surviving links after purge); they are never returned as authoritative counts.

Inbox, mark-read detail and snapshot reauthorize sources in batched SQL aggregates: **at most 200 notification IDs per query**, returning at most 200 constant-size aggregate rows, each with one earliest visible source (created_at/id), an exact visible count and summary flags. No per-notification query loop or unbounded source decoding is used. Counts, categories, actors and references include every authorized source, even above 200; all-hidden rows disappear. Exact counts still require the database to inspect all linked sources under its statement timeout—the cap bounds decoded rows/query, not ACL checks or total snapshot size. Snapshot remains complete, using successive batches in its existing REPEATABLE READ transaction. The raw-source preview helper is separately capped at 200 sources and is not used for inbox counts. `audit_bl_digest.rs` pins source decode/query counts across the 500-event consumer boundary, restart/late delivery and multi-batch reads, plus visibility loss above the cap.

### Delivery limitations and database permissions

- Accepted limitation: a held digest's source categories are gated when consumed, not re-gated at release. Disabling Activity/Assignments/Dependents after consumption does not remove those sources from a held digest if Digest remains enabled. Digest itself is rechecked at release; already-released history is never rewritten by preference changes.
- Event dedupe retention is 90 days (R74). Server reminders are emitted, and carried across regeneration, only while `fire_at` lies inside that horizon (`fire_at > now - 90 days`); an emitted event's created_at is >= fire_at, so every in-horizon tuple still has its dedupe witness and an overdue reminder cannot re-fire after retention deletes the event. The horizon is the single constant `porchlight_db::derive::NOTIFICATION_EVENT_RETENTION_DAYS`, used by the notifier scan and the derive CTE; a db unit test pins it to the interval hardcoded in `pl_retention` (0056). Cost: a reminder missed during a notifier outage longer than 90 days is never delivered (the item still shows overdue).
- `porchlight_app`: notifications SELECT/INSERT/UPDATE/**DELETE** (0062); notification_sources SELECT/INSERT; notification_prefs SELECT/UPDATE. DELETE is confined to the generated inbox table needed for irreversible held-digest suppression, not events, explicit source deletion, prefs, or authoritative items. Existing source-link FK cascade removes only links of deleted notifications. Agents retain SELECT-only inbox/source/prefs grants; maintenance retains its existing purge/retention grants. `server/db/tests/protocol/invariants.rs::EXPECTED_GRANTS` is the checked relation-ACL inventory. Migration 0065 changes only delivery constraints (zero grace strikes and statement_cancel); app/agent grants remain exactly those from 0023. Notifier regressions (`m5_regressions.rs`, the `notifications.rs` suite and the stream notification helper) execute consumption/release as the production app login so privilege failures cannot hide behind the fixture superuser.

## Desktop native delivery limitations

Desktop Notify replies are owned independently of stream/session jobs. Failed pre-send inventory writes restore the
pre-attempt row and undo any possibly committed in-flight marker before retrying; unavailable rollback storage keeps a
repair obligation ahead of further native work. Definite submission failures, bus errors proving non-delivery (such as
ServiceUnknown/NameHasNoOwner), and notification-service rejections restore the matching pending row. Definite failures
retry after 1 second, doubling to a five-minute cap, reset by success or a notification-server owner change. Without a
notification-server owner, no posts are prepared, written or attempted; the owner-change callback wakes delivery.

D-Bus NoReply, Timeout, TimedOut, Disconnected, and transport loss after submission remain ambiguous, not definite
rejections. Classification uses error names and sender, not message text. These versions are not blindly resent,
including after restart on the same daemon. Disconnect finalizes outstanding futures as ambiguous and releases their
in-memory reply ownership, retaining durable suppression. A newer server version may post despite an ambiguous older
version (its content changed); a late older handle is withdrawal-only.

Normal shutdown stops new native work, then drains outstanding replies under one total 2.5-second deadline. This
outlasts an already-running native call's two-second bound so a received handle can reach disk despite runtime-lock
contention. Handles or retired-row withdrawal tombstones are persisted before bus/completion-scope teardown. This is
not a total quit-time guarantee: dbus-java disconnect may additionally wait up to ten seconds on receiver executors.
There is an inherent cross-process gap: `org.freedesktop.Notifications` allocates IDs on the server and provides neither enumeration nor client-chosen IDs.
If the process is killed after send but before learning/persisting the reply, or no reply arrives within shutdown's
budget, a daemon may retain a visible notification whose handle cannot be recovered. On identity change an unresolved
handle-zero row is dropped without resending or blocking admission; this is not proof of native withdrawal. The owner
may need to dismiss that notification manually (or restart the notification daemon). Inbox remains authoritative.

## Safe presentation (R57)

There are two deliberately distinct vocabularies: top-level delivery `category` is one of reminders/assignments/dependents/activity/digest/connection and controls preference gating and delivery semantics; `summary.category` is the presentation topic (reminders/assignments/dependents/activity/digest/comments/conflicts/operational). **Clients use `summary.category` for UI topic grouping**, not the delivery channel. Do not treat a comments/conflicts/operational topic as a new preference channel.

Every known event kind has a fixed title/body template; unknown kinds render generic household activity, not a kind name or payload string. `summary.text` remains the concise CLI rendering; `summary.title`, `body` and `category` provide presentation topics. `summary.category` is distinct from the six unchanged **delivery/preference channels** in the top-level notification category: comments/mentions → comments; hard/load conflicts → conflicts; feed/derivation errors → operational; suggestions/calendar/status/completion → activity. All four topics use the spec's Household activity delivery channel, so no schema/category/preference expansion is made. Reminders/assignments/dependents/digest retain their channels/topics. A load payload with `conflicting:false` renders “Availability restored / Load back within availability.”; only that boolean is projected from payload, never text/URLs/secrets. Reminder and dependent multi-source summaries describe reminders/alerts, not item updates; singular digest says “1 update”. Terminal errors have a fresh opaque non-item entity UUID.

## S5 revert integration

`POST /v1/admin/items/{id}/revert` / `porch revert` restores authoritative item inputs through the ordinary `items::WriteScope` / `begin_at` / `finish` path within the actor-attributed mutation transaction. No direct notification writer or duplicate emitter is needed: the 0006 task-event triggers → 0020 `task_notification` producer sees restored assignments, and ordinary derivation emits hard conflicts and rebuilds reminder inputs. Revert restores relationship **deltas**, retaining unchanged assignees/viewers/reminders; no-op and field-only reverts do not emit duplicate assignments. The agent label and HTTP PAT's authenticated owner attribution are preserved, with the shared recipient/self-suppression rules.

Item revisions do not contain occurrence status/completion history: revert does not overwrite those authoritative occurrence fields or manufacture status/completion notifications. Ordinary occurrence writes still use the same task-event producer. Reminder/dependent notifications retain their normal scheduler timing, not an immediate revert-specific producer. `admin_domain` regressions cover restored assignments with actor/task dedupe linkage, unchanged-assignee/no-op suppression, retained occurrence completion, and new hard-conflict emission plus canonical-pair dedupe.

O2 migration 0055 explicitly counts/severs selected `notifications` item/occurrence references and deletes selected `notification_sources` / `notification_event_delivery` before their parent events. Recipient history and unrelated coalesced sources survive. The R56b closure guard still refuses future unknown relations before audit/domain changes. Nightly 90-day retention explicitly counts source/delivery children before old notifications/events; [O2 contracts](data-out.md) define clock boundaries and audit counts.
